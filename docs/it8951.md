# IT8951 screens

The IT8951 driver shows images on e-paper screens with the IT8951 controller chip, as sold with Waveshare's IT8951 HAT (the board between the Raspberry Pi and the screen).

| Model (`model=`) | Size in pixels | Status |
|---|---|---|
| `"6"` | 800 × 600 | untested |
| `"7.8"` | 1872 × 1404 | untested |
| `"9.7"` (the default) | 1200 × 825 | tested |
| `"10.3"` | 1872 × 1404 | untested |

"Tested" means the driver was run on that screen: start, full writes, fast writes (also checked by eye), clear, time limits and releasing the pins. "Untested" means it should work but has not been run on a real screen. Reports are welcome. The 7.8" and 10.3" have the same size in pixels, so the driver cannot tell them apart; choose the one you have.

## Install

epdlib version 1 is not on PyPI yet (`pip install epdlib` gives the old version 0.6). Install it from GitHub, together with the `it8951` install group, which adds `gpiod` and `spidev`: the libraries for the Raspberry Pi's pins and for its SPI connection (the wired data connection to the HAT).

1. Turn SPI on: `sudo raspi-config`, then Interface Options, SPI, then restart the Pi.
2. `spidev` is built on the Pi when it is installed, which needs a C compiler and Python's header files: `sudo apt install gcc python3-dev`.
3. Raspberry Pi OS does not let `pip` install into the system's Python, so make a virtual environment (a folder that holds one program's own packages) and install there:
   ```bash
   python3 -m venv ~/epdlib-venv
   ~/epdlib-venv/bin/pip install "epdlib[it8951] @ git+https://github.com/txoof/epdlib"
   ```

For working on epdlib itself: `uv sync --extra it8951` (plain `uv sync` leaves out `gpiod` and `spidev`).

The driver uses only GPIO 17 (reset) and GPIO 24 (busy) and SPI bus 0, device 0 (`/dev/spidev0.0`). These are GPIO numbers, not pin positions on the header. Chip select (the pin that tells the controller "this transfer is for you") stays with the kernel's SPI driver. So a HiFiBerry DAC+ (a sound card board that uses GPIO 2, 3 and 18 to 21) can be on the same Pi.

## Use

```python
from PIL import Image
from epdlib.drivers.it8951 import IT8951Driver

image = Image.open("picture.png").resize((1200, 825))  # must be the screen's size
next_image = Image.open("picture2.png").resize((1200, 825))

with IT8951Driver("9.7", vcom=-1.90) as screen:
    screen.write(image)  # full refresh
    screen.write(next_image, fast=True)  # only the part that changed
    screen.sleep()
```

The image is reduced to the screen's 16 grays. The `with` block starts the screen (`init`) and always releases the pins and SPI at the end, even after an error. `sleep()` puts the screen into low power; the next `write()` or `clear()` wakes it without a reset, so the driver still knows the last image and a fast write after sleep sends only the changed part. Call `init()` again only after `close()`.

## Settings

**`model`** (default `"9.7"`): which screen, from the table above. At start the driver checks that the controller reports that screen's size.

**`vcom`** (required): a voltage that each screen needs set for good contrast. It is printed on the screen's flat ribbon cable, for example `VCOM = -1.90V`. Use that number, with its minus sign. A wrong value gives washed-out or too dark images. There is no default, because every screen has its own value. Values from -3.0 to -0.5 are accepted, the range Waveshare's screens are printed with.

**`max_refresh`** (default 4): after this many fast writes in a row, the next write is a full one. Fast writes leave faint leftovers of earlier images; a full write removes most of them. 4 is the recommended value. Higher numbers flash less often but leave more leftovers; 0 means never force a full write: then call `clear()` or a full `write()` yourself now and then, for example once an hour. A fast write that covers the whole screen with GC16 counts as a full one.

**`fast_gray_mode`** (default `Mode.GL16`): the mode for a fast write whose changed rectangle has grays. It is set on the driver, not when making it, for example `screen.fast_gray_mode = Mode.DU4`. Checked by eye on the 9.7" with a clock (dark text on white) and a word clock (white text on black):

| Mode | Text | Flash | Time for a clock tick |
|---|---|---|---|
| `Mode.GL16` (default) | sharp, smooth curves | none on light backgrounds; a box flashes around the change on dark backgrounds | about 0.6 s |
| `Mode.DU4` | **jagged curves and slanted lines, with odd marks**, clearly worse than the rest of the screen until the next full write | little or none | about 0.4 s |
| `Mode.GC16` | sharp, smooth curves | a box flashes around the change, also on light backgrounds | about 0.6 s |

Choose DU4 only when no flashing matters more than how text looks. The numbers of GL16 and DU4 were checked on the 9.7" only; on other IT8951 screens they may select a different mode.

**`timeout`** (default 15 s): the longest one operation (`init`, `write`, `clear`) may take. **`ready_timeout`** (default 2 s): the longest one wait for the controller's busy line may take; only the wait after the reset at start may take up to 5 s. When a limit runs out, the driver raises `DisplayTimeout`. It never waits forever.

## Refresh types

| Call | What the screen does |
|---|---|
| `write(image)` | Full refresh of the whole screen, 16 grays, with a flash (GC16, about 1 s). |
| `write(image, fast=True)` | Only the smallest rectangle that changed is sent. Black and white only: no flash (DU, about 0.4 s). With grays in that rectangle: `fast_gray_mode` (GL16 by default: no flash on light backgrounds, a box flash on dark ones), because DU shows black and white only. Nothing changed: nothing is sent, and it does not count toward `max_refresh`. |
| `clear()` | Long flash to white (INIT, about 2 s). Removes all leftovers of earlier images, also those a full refresh leaves. Do this now and then, for example once an hour, then write the image again. |

The first write after `init()` and the first write after an error are always full, because the driver then does not know what the screen shows.

Text is drawn with smooth edges, which are gray pixels. So a fast write that changes text usually counts as "has grays" and uses `fast_gray_mode` on its rectangle.

Fast writes are smallest over plain black, white or flat gray areas. Over a photo or a gradient, the image is dithered (dot patterns that fake in-between grays), and a small change can change the dot pattern down to the bottom of the screen, so the rectangle gets much larger.

## Errors

| Error | Meaning |
|---|---|
| `ValueError` when making the driver | A setting is wrong, for example `vcom` missing. The message says which. |
| `DisplayError: /dev/spidev0.0 is missing` | SPI is off: see Install, step 1. |
| `DisplayError: cannot claim GPIO17 and GPIO24` | Another program is using these pins. Stop it first. |
| `DisplayError: no answer from the screen` | The controller sent nothing back: check the cable and the HAT. |
| `DisplayError: the controller reports ...` | The screen's size does not match `model`: choose the right model. |
| `DisplayError: image is ...` | The image is not the screen's size. |
| `DisplayError: screen is closed` | `write` or `clear` after `close()`: call `init()` first. |
| `DisplayTimeout` | The screen did not finish in time. Call `init()` again to reset it. |

## Hardware test

With the screen attached:

```bash
EPDLIB_IT8951_VCOM=-1.90 uv run pytest -m hardware tests/test_it8951_hardware.py
```

For another screen, also set `EPDLIB_IT8951_MODEL`, for example `EPDLIB_IT8951_MODEL=6`. Without `EPDLIB_IT8951_VCOM` the test is skipped. It draws a test page, a few fast updates and a clear, and checks that each one finishes within its time limit. It ends with a clear (a long flash to white).
